# Store MCP acquisition and update foundation — 5 October 2026

Branch: `extensions/tool-only-retirement`. E2 remains in progress. This is backend acquisition evidence, not certification of the complete store-MCP feature or a production release.

## Implementation

- Signed catalogue entries explicitly distinguish `artifact_kind: "mcp-descriptor"` from legacy native packages. Missing kind retains native encoding; unknown kinds fail parsing. The native installer refuses descriptor artifacts.
- A descriptor artifact is at most 8 KiB, fetched as `blob/<sha256>.mcp.json`. Its size, hash, ID, version, name and description must match the verified catalogue. MCP entries cannot carry native permissions/host contributions or self-declared unreviewed trust.
- The existing store freshness, revision, cancellation, revocation and HTTP byte limits guard acquisition. Final developer consent and catalogue state are rechecked before atomic publication. No MCP endpoint, OAuth browser, credential or worker is started by acquisition.
- The existing connection registry preserves original descriptor bytes and hash. Store connection/account IDs are generated by the host in a distinct `mcp:v1:store:<extension>:<connection>:<account>` namespace. Restart validates those bytes and their definition; failed saves preserve old state.
- Duplicate store acquisitions and direct JSON edits are refused. Removal uses the same registry/account cleanup path; namespace pruning now derives from the record instead of assuming configured ownership.
- `store_mcp_install` is main-window and Developer Mode gated. Store records remain inactive: connect, enable, runtime execution and Agent directory publication cannot activate them before the combined store acceptance checkpoint passes. The existing native store UI does not display descriptor cards yet.

Stored provenance is a host-profile record, not an independent signature certificate. Acquisition starts from `StoreState`'s verified catalogue; the private admission value only proves artifact/hash/metadata consistency. Publisher JSON cannot construct a trusted host source. No SDK/OAuth replacement or physical legacy removal occurs.

## E2h: verified update and revocation ownership

`store_mcp_update` requires the main window, current Developer Mode consent and exact installed revision. It selects the requested version from the verified fresh catalogue and reuses acquisition's bounded download/hash/identity/final freshness gate; callers cannot supply descriptor bytes, source or trust. A removed, edited or reacquired connection cannot be overwritten by a delayed download.

An identical artifact is a no-op. A changed artifact invalidates outstanding work and removes enablement before publication. Metadata-only changes preserve the account; endpoint/authentication changes retire the three exact owned vault records and configured client metadata before allocating a fresh account. Registry publication remains atomic. Cleanup/save failures preserve the previous descriptor; cancellation, disablement or successful credential deletions are deliberately not rolled back. Recovery may require reconnecting the old account; no failed update is reported as successful.

Resident signed revocations now participate in store `RuntimeOwner.current()` and therefore the existing vault-publication guard. Missing policy fails closed. Exact-version and all-version revocations refuse old owners even before generation/settings cleanup; another ID/version and deprecation do not revoke an existing account. After store refresh, cancellation/disablement applies only to matching store records, including cached revocations. A failed settings save does not stop attempts to cancel the other revoked records, and the runtime policy still refuses them. Configured/catalogue account ownership remains separate. Revoked descriptor/grant data is retained for explicit removal; this is disablement, not silent deletion.

Scoped source audit traced final catalogue ownership → connection mutation → cancellation → settings/vault retirement → atomic save, and resident revocation → copied runtime owner → actual `VaultCredentialStore.commit`. Lock order is store ownership then connection operation then short registry/control access; runtime policy only reads the revocation lock and never reacquires store ownership. No network await holds either mutation lock. Review corrected cross-record cleanup continuation and kept configured owners from retaining the store policy reference. Graph reports supplied structural guidance, not acceptance evidence; their zero-flow/test-gap estimates do not replace source review or executable checks.
