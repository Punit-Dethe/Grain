## Adapter adjustment and review

The adapter first requests foreground focus and observes it for a bounded interval. If still absent, it can activate the actual owned Agent through one empty-header click. Window enumeration requires a unique visible `Grain Assist` window belonging to the owned host PID. Window-from-point/root checks refuse an obstruction; the owned PID, visible title and point/root identity are checked again immediately before input. Header lookup temporarily uses per-monitor DPI awareness and restores the helper thread context afterward; both mouse events carry absolute virtual-desktop coordinates rather than depending on later pointer movement. Held modifier, Escape or left-button input is refused. Actual foreground identity remains mandatory before sending one Escape down/up pair. No foreign window titles or PIDs are read into evidence; no typed text or cursor coordinates are retained.

The pointer stays at the owned header after the click. Immediately restoring it could redirect queued mouse input. A partial down-only insertion attempts a matching synthetic release as cleanup and remains a failure; user-held inputs are never released. There is no key, tool or scenario retry, focus privilege hook, extra keyboard listener, or production focus change. Observation and execution timeouts remain finite. Input evidence is retained even if later host-status collection fails, and errors before JSON output retain their original diagnostic.

The explicit `--focus-click` option is admitted only for `agent.reopen-escape`, recorded in the adapter identity, and asserts accepted click counts on all ten pairs. It exercises the click path even when direct foreground activation succeeds; it does not prove every Windows foreground-denial condition. No artificial delay is inserted between old-window cleanup and replacement registration.

## References and limits

Microsoft documents [foreground activation restrictions](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow), including denied calls even when stated conditions appear satisfied. That supports recording denial separately, not blaming user activity without evidence. [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput) reports inserted events and retains existing key state; it does not confirm downstream execution. [LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc) documents hook-chain blocking and timeout removal; these are diagnostic possibilities, not observed causes here. Reviewed the pinned `handy-keys` 0.3.4 listener/manager source and Grain's transient registration/generation guard and `global_close`; [upstream library](https://github.com/handy-computer/handy-keys) supplies context, not evidence of a particular local failure.

[GetWindowRect](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowrect) documents DPI virtualization; [SetThreadDpiAwarenessContext](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setthreaddpiawarenesscontext) permits a temporary helper-thread context. [MOUSEINPUT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-mouseinput) defines normalized absolute virtual-desktop coordinates. These references informed the adapter safeguards; no monitor configuration or application DPI policy was changed.

The accepted-input/window-timeout observation remains open. Future occurrences now retain the input-stage facts needed to distinguish setup denial from delivery/handler failure. Do not close it merely because subsequent runs pass, and do not mark the existing acceptance ledger complete. Foundation feature work remains paused.
