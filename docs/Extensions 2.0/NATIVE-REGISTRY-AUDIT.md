## Procedures and boundary

The maintained `registry-recovery` suite combines three real-application scenarios. Each runs the real isolated Tauri/WebView2 host and actual permission/Agent approval/executor paths, using only its fixed permission-free native tool. Files are mutated only inside the owned profile, with the host stopped before startup fixtures are changed. The binary/source stamp from the preceding unit remains valid because application sources are unchanged.

- **`native.registry-refusal`:** extends the existing real startup case to malformed JSON, a future migration version, inconsistent map/record identity, and an 8 MiB plus one-byte file. Each must keep its source bytes, report a registry-load diagnostic, expose unavailable extension operations and spawn no worker. Restoring saved bytes after the owned host exits must recover the actual greeting. Four independent refusals and recoveries give eight real restart transitions.
- **`native.registry-preservation`:** compares the actual saved installed record across restart, including a synthetic opaque native account pointer. Disabled state retains its record/pointer and starts no worker. Corrupting only the owned current artifact while stopped makes real startup quarantine it; it stays disabled and loses declaration approval. Restoring artifact bytes does not silently lift quarantine or approve/enable it. The record/refusal reason, artifact and a profile-data sentinel survive another restart. Explicit validated import and fresh real consent restore the actual tool across restart.
- **`native.registry-save-failure`:** a short-lived owned PowerShell helper opens the actual registry with read/write sharing but denies delete sharing. Production atomic publication receives its normal bounded retries and fails. Failed enablement remains disabled in memory/on disk/across restart. Failed disablement stops the live tool, reports failure and preserves the old enabled disk state; restart honestly reflects that old state. A subsequent successful explicit disable persists across restart, and a fresh explicit enable/greeting recovers. Neither schedule retries a tool call.

Check 49 concerns registry preservation, including its account pointer field, rather than provider/account validity. The opaque pointer is a fixed nonsecret 32-character value; no matching credential is created, connected or refreshed. Its preservation proves registry serialization/startup ownership only. It does not certify a valid OAuth grant, native account switching, provider identity, credential-vault durability or check 53's conditional development/installed account flow. That account portion remains Pending/Blocked on its separate fixture and account prerequisites.

The sentinel is unrelated inert data in the isolated profile. It demonstrates that this refusal/recovery procedure preserves neighboring data; it is not a comprehensive extension-storage, settings or R1 upgrade certificate. Artifact corruption occurs only while the owned host is stopped. No real profile permissions, registry or packages are changed.

## Multi-source references

[VS Code's extension management service](https://github.com/microsoft/vscode/blob/main/src/vs/platform/extensionManagement/node/extensionManagementService.ts) is a primary-source reference for scanning invalid extensions, profile state and publication/error handling. Grain's preserve-and-refuse policy is its own narrower contract, not a copy of VS Code's repair behavior. Grain continues using its existing small JSON registry, not a newly introduced database. [Microsoft's ReplaceFile documentation](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew) supplies sharing/access/error context for the real Windows lock fixture; production replacement is still the existing Rust/tempfile implementation. These are independent relevant primary sources, not an unverified star ranking.
