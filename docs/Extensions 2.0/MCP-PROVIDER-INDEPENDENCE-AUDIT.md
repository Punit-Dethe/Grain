## Contract and references

[Procedure 14](MCP-EXTENSION-PLAN.md) requires overlapping dynamic-registration logins, completed versus cancelled accounts, independently usable read tools, isolated disable, and explicit refusal of competing preregistered logins on Grain's fixed callback port with serial recovery. This controlled procedure does not certify a particular personal account or browser consent interface; eligible live-account checks 9/12/17 remain separate.

The [MCP authorization specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) requires resource indicators and token audience validation; [RFC 8707](https://datatracker.ietf.org/doc/html/rfc8707) explains binding a grant to its resource. The [official Rust SDK authorization source](https://github.com/modelcontextprotocol/rust-sdk/blob/main/crates/rmcp/src/transport/auth.rs) is the delegated SDK boundary. [Goose's environment-variable guide](https://github.com/aaif-goose/goose/blob/main/documentation/docs/guides/environment-variables.md) documents configurable callback ports for redirect registration. These references inform exact origin, callback and account assertions; no SDK upgrade or new authorization engine is adopted.

The graph flags broad dependencies and incomplete test edges; zero affected flows is not a safety certificate. Direct source/diff tracing checks marker admission, catalog feature gates, HTTP construction, consent guard ownership, production `ConnectGuard`, per-provider tickets/vault keys, dynamic versus fixed listener binding, disable/disconnect and Agent result continuation.

## Implementation and limits

Only maintained acceptance infrastructure and feature-gated catalog branches change. Two fixed peer IDs, a second validated marker port and four finite consent slots replace the former single test handoff. The exact provider slot is consumed independently; a stale owner cannot clear a newer owner or another provider. No arbitrary provider/endpoint/token access or approval bypass is added. Ordinary/release builds exclude these catalog entries and controls. Handy/frontend/model settings and production timers remain unchanged.

The second server reuses the existing owned HTTPS peer and run certificate; its origin/port, client/code/token maps and account are separate. Both verify actual resource/PKCE exchange; bearer tokens are recognized only by their own issuer map. The model selects exact metadata/schema for its fixed provider, then the actual React confirmation dispatches the read. Each read must return the expected actual account/nested JSON, one independently recorded provider call, zero other-provider calls and a model receipt belonging to that provider. Reports retain only bounded metadata, never bearer tokens, consent URLs or authorization codes.

| Case | Exact schedules |
|---|---|
| `mcp.auth-provider-independence` | Two real DCR futures/listeners open together; complete A while B stays pending, read A, cancel B and reject its issued late callback with zero exchange/grant; connect B freshly, read both, restart both without new login; disable A's pending approval, refuse it without wire traffic, preserve B reads; disconnect A, restart and verify B again. |
| `mcp.auth-fixed-port-conflict` | Two fixed preregistered clients on distinct issuers; while A's callback listener owns port 31938, B must report the exact port conflict with no handoff/exchange/grant/enable and preserve A's flow; complete/read A, retry B serially on the released exact port, read both and restart without reauthorization or DCR. |

The Agent permits one active request. Login futures may overlap an approved independent Agent read, but this does not promise two simultaneous Agent requests. Consent replaces only the external browser handoff; the SDK creates/verifies PKCE/state/resource, the actual loopback listener accepts callbacks and the production vault stores grants. No shortened production deadline, fabricated grant or reused ordinary profile accelerates acceptance.

`mcp-independence` selects both cases in one host; `mcp-auth` selects eight and `mcp-foundation` seventeen. New cases run after the earlier client-configuration case, avoiding a false empty-client prerequisite in a combined batch. Stage counters use actual per-scenario baselines. Ordinary `all` now selects 71 of 80 maintained IDs; official/public/genuine-model cases keep their opt-in prerequisites.

## Oracles, retention and verification

`wrong-mcp-peer-account` is confined to the isolated independence case and changes the peer's actual bearer-account result; its exact account oracle must fail. `skip-fixed-port-conflict` is confined to the fixed-port case and omits the competing connect attempt; the missing explicit-refusal assertion must fail. Neither is accepted as positive coverage. New self-tests reject cross-provider metadata, wrong account/wire/result receipts and cross-unit fault admission. Rust guards test the distinct enabled peer port and generation/provider slot isolation.

Retain these fixed controls and assertions as reusable acceptance infrastructure. Two listeners exist only for selected independence cases; all held responses, issuer maps, timers, credentials, WebViews and disposable profiles must be retired. Metadata-only cleanup uses the exact run namespace and four fixed grant/secret keys; it never reads credential blobs. See [retention inventory](AGENT-TEST-HARNESS.md). No unused production scaffold is introduced.
