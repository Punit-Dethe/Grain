# Signed registry metadata renewal

Date: 6 October 2026. Branch: `extensions/tool-only-retirement`.

## Scope, decision and plan

Continue E4 operational maintenance on the user's confirmed GitHub registry host.
The optional public OAuth website PR is parked; no website, registry host, app
bootstrap, SDK, author contract, runtime or trust-key change is part of this unit.

Execution: graph/source and primary-source review → one maintainer CLI command
reusing existing verification/signing/assembly/promotion → focused signed expiry,
preservation and refusal cases plus maintainer regressions → actual production
CLI admission checks → scoped audit → pinned Linux checkpoint → docs/commit/push.
No new Agent harness engine, scenario or manual test batch.

The existing serving path could consume externally renewed signed metadata, but
there was no narrow command to produce a renewal without invoking the legacy
publishing/retirement paths. Add `renew-serving-metadata`; it changes only index
and revocation metadata versions/expirations. It preserves all entries, arbitrary
future JSON fields, revocation states/reasons, publishing roots/signatures and
referenced artifact/description/media bytes. No extension is rebuilt, admitted,
withdrawn, reapproved, deleted or published.

## Implementation and operating contract

```powershell
grain-registry renew-serving-metadata --v1 SELECTED_SNAPSHOT --expected-snapshot-sha256 INDEPENDENT_SNAPSHOT_PIN --key OPERATOR_PUBLISHING_KEY --expires-days 30 --out FRESH_RENEWAL
grain-registry verify-serving-tree --v1 FRESH_RENEWAL/v1
grain-registry promote-serving-tree --assembly FRESH_RENEWAL --store PROTECTED_STORE --expected-current-sha256 INDEPENDENT_CURRENT_POINTER_PIN
```

The expected snapshot digest comes from the independently protected selected
store/handoff (or the verified snapshot inventory), not an untrusted received
hash. The command verifies the actual app-pinned roots, both old publishing
signatures, strict metadata/asset bounds and every addressed file. It compares
the complete six-document-plus-addressed-inventory snapshot identity before any
key read. Expired index/revocations can be recovered; expired roots require a
separate root-authorized recovery and are refused before key access. No CLI root
override was added.

Lifetime is one through thirty days. Both metadata expirations must advance;
metadata versions increment by exactly one, with checked exhaustion. Long-lived
2099 seed documents deliberately refuse renewal rather than silently shortening
their validity. Serialization uses the original generic JSON documents, preserving
unknown envelope/entry/rule fields, with only `version` and `expires` replaced.
The same existing 4 MiB per-document bound applies to the generated bytes.

Only then is a regular, non-linked key file read through the existing 8 KiB
bound. The existing minisign signer is reused, and both resulting signatures must
verify under the existing root-authorized publishing key before any output is
created. The signer still supports the existing unencrypted maintainer key
format; no KMS/HSM, new key store or production custody approval is claimed.
The key string is dropped before asset copying; secure-memory erasure is not
certified by dropping a String. No secret/key content is logged.

Output is a fresh assembly directory outside the source, containing complete
`v1/` and its exact previous-parent `promotion.json`. Existing streaming copy,
byte verification, resulting freshness/transition checks and directory sync are
reused. Partial owned output is cleaned by the existing RAII guard on failure;
inputs and existing outputs are preserved. This adds no service, background
thread, idle timer, permanent cache or dependency. At most bounded document
buffers plus the existing one-file streaming buffer are live.

Local promotion independently binds that parent to the locked current selection,
checks metadata/history/revocation monotonicity and retains the old snapshot.
The resulting hosting bundle includes expired signed historical proof and old
addressed assets. An independent snapshot pin is input identity, not source-review
or release authority: the operator's key and eventual protected workflow remain
privileged. Renewal cannot add/reapprove extensions; approved source additions
must still go through `sign-reviewed-candidate`. Remote GitHub commit activation,
release review/protection and coherent client reads remain separate gates.

## Remaining delivery work and sources

This closes the renewal producer within the documented maintainer scope.
Hosted GitHub activation/coherence, earlier protected
history migration, actual independent source approval-to-signing and enforced
repository/workflow/key custody remain E4 prerequisites. Scheduled/protected
renewal execution, emergency revocation issuance/deployment and root-expiry/key
rotation operations still require separate implementation/operational acceptance.
There is no timer that automatically opens keys or publishes. The existing
incomplete legacy publisher is unchanged; do not merge into it or use held
physical removal as a shortcut.

**Five E4–E8 stages retain work**. Baseline **52 Pass / 1 Deferred (12)**, latest
forward **71**, public OAuth **56 Pending**, Agent inventory **108 / 93 / 81** and
the physical obsolete-code removal hold are unchanged. E5 management/store UI,
E6 runtime recovery, E7 measurements/integrations and E8 certification follow.

Primary sources checked 6 October:

- [TUF 1.0.36 specification](https://theupdateframework.github.io/specification/latest/): expiry, monotonic versions, immutable targets and metadata-update operations inform renewal; Grain is not claiming TUF conformance or adopting a second framework.
- [Existing minisign implementation](https://github.com/jedisct1/rust-minisign): reuse the locked signing library and existing client verifier, rather than a new signature implementation.
- [GitHub Git reference API](https://docs.github.com/en/rest/git/refs): hosting activation is a separate repository reference operation; local renewal is not remote concurrency/branch protection evidence.
