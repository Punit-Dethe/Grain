# Preregistered MCP client ownership

3 October 2026. Focused follow-up after B5b. Tool calling, client metadata document deployment, typed recovery UI, physical retired-capability removal and genuine Linear expiry are outside this slice.

## Plan and reference requirements

1. Trace credential Save, explicit Connect, stored-grant initialization and logout. Use graph first, then source/SDK traces because the graph supplies no affected flows for this boundary.
2. Extend the maintained two-peer fixture to rotate the authorization server for one unchanged MCP resource. Observe actual token requests using nonsecret receipt flags. Reproduce the missing protection before claiming disclosure; a source storage gap alone is insufficient.
3. Persist preregistration ownership independently of grants. Keep existing client-ID settings and client-secret vault formats. Add a bounded versioned issuer/client-ID record in the OS vault; publish it under the existing generation/operation lease after clearing the prior binding before any secret replacement. Reject absent/legacy/mismatched records before loading or supplying the secret to the SDK.
4. Bind on explicit credential Save using validated SDK discovery, with a finite absolute deadline and no browser or credential transmission. Discovery failure preserves previous configuration/grants. Disconnect clears tokens but retains the registration binding. A changed issuer requires explicit new registration credentials and Save; never silently rebind on Connect.
5. Add logic, debug-marker/admission, real-app rotation/restart/recovery and negative-oracle coverage. Repeat affected suites, review changes, independently inspect scoped resources and document exclusions before commit/push.

The current [MCP client registration standard](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration#authorization-server-binding) requires exact authorization-server issuer ownership for preregistered/persisted client credentials and refusal of cross-server reuse. [Authorization response validation](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#authorization-response-validation) separately protects code callbacks; it cannot substitute for persisted preregistration ownership. [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html) provides the OAuth security baseline. The official [Rust SDK 3.5 auth source](https://github.com/modelcontextprotocol/rust-sdk/blob/rmcp-v3.5.0/crates/rmcp/src/transport/auth.rs) supplies discovery, registration and grant ownership. [Pinned OpenCode integration](https://github.com/anomalyco/opencode/blob/c42ae0d56b6f86f8df39d451d6d2cfe6414b3928/packages/opencode/src/mcp/oauth-provider.ts) also separates registration from grants and scopes stored registration by server URL; configured clients return directly, so that code is not proof of exact issuer protection. Grain retains OS-vault storage and uses the protocol's issuer key rather than copying file persistence or treating server URL alone as sufficient.

Release/ordinary builds contain no such admission. Guard tests must refuse absent peer/auth markers, third origins, wrong paths/schemes and embedded credentials.

They are not disclosure evidence: the prior debug guard correctly admitted only the provider's own origin. Their credential/scratch cleanup passed. A focused guarded admission extension is needed to model an authorization server different from the MCP resource, which the protocol permits. No ordinary-account grants are copied or credentials shown in evidence.

Peer receipts retain only token-request counts, presence and known fixture-secret version flags. The new metadata namespace must be included in exact-marker credential cleanup/inventory even for public clients, whose registration records contain no secret. Existing long-term fixture ownership, disposal and scenario IDs remain; the new scenario has its own requirement after the original 53 rather than rewriting the deferred Linear requirement.

## Reproduction and implementation

`run-Aw1bMV` runs the unchanged production MCP implementation with only the guarded fixture admission added. After MCP resource A changes its advertised authorization server to B, explicit Connect succeeds unexpectedly: B records `token-attempt`, `secretPresent: true`, `secretVersion: 0`, followed by a successful confidential token exchange. Those are known synthetic fixture flags, not secret values. Cleanup Pass. This confirms actual cross-issuer preregistration reuse, rather than inferring it from source or counting the earlier admission failures as proof. Baseline binary `37ccecec8a6eb98741d442214eb84f6bc7ae5f636b52a6cf3f87243308223f30`, source `0bce94d31610c016e3fbd750f8585fd8fa79831b77c0318469b05f39a69c6f9f`.

Production now stores `{schema: 1, client_id, issuer}` under OS-vault service `com.grain.mcp.client-registration`, keyed by provider, independently of `StoredCredentials`. The record is bounded to 8 KiB, versioned and strict about unknown fields. Client and issuer are exact strings; equivalent-looking URLs are not silently normalized. Save uses the existing SDK and bounded no-redirect HTTP client, with no client configuration/credential store supplied to discovery. Its 90-second absolute deadline includes the provider queue and network discovery. A failed or unusable discovery never mutates settings, the previous secret, registration or grant. It still invalidates in-flight operations, as credential edits already did.

After valid discovery, the existing provider lease/generation guard disables the provider and publishes in this order: clear old grant → remove old registration binding → replace/remove secret → write new binding → update configured client ID. Thus a partially failed vault update either retains the old secret pair or removes ownership before any replaced secret can be used. Matching the configured ID refuses partial settings publication. Zeroizing ownership covers the secret during discovery, cancellation and blocking writes; detached vault tasks retain their lease and check generation. Synchronous OS-vault calls themselves are not preemptible; no claim of interrupting a stuck platform API or cross-process locking is made.

Explicit Connect checks the registration before opening consent or loading a secret. Stored-account initialization checks before SDK credential initialization/configuration, so refresh cannot receive a foreign preregistered secret. Disconnect removes tokens and retains the registration metadata, including for public clients. Missing, corrupt, future-version, oversized or mismatched bindings are refused. Existing preregistered configurations have no trusted issuer record and therefore require one explicit credential re-save; there is no silent migration or repeated daily sign-in requirement. Dynamic registration (including Linear) is unchanged. Existing settings/client-secret/grant formats and frontend command signatures remain unchanged; no dependency, idle service or new application engine is added.

The cleanup helper inventories only exact owned UUID services and the four fixed MCP test accounts, never credential blobs. Its standard MCP teardown removes grant, secret and registration namespaces and asserts all three remaining counts are zero. The new registration-only inventory includes public clients. Existing selectors, journal bounds and zero-secret public-client checks remain; `mcp-auth` now has eleven cases, `mcp-foundation` twenty and the two-peer subset three.
